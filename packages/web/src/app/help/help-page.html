{{ sec.what.n }} {{ sec.what.label }}

Autocode is a framework for long-term, agentic autonomy: it lets AI coding agents keep working on their own for days or weeks, coordinate with each other, and stay under your control. That purpose decides which features it has:

What an Agent Needs What Autocode Has
come back later, with nobody prompting it wakes: on a schedule, at a time or when idle, with checks that decide whether to wake
react when a background job ends a fire-only wake that the job fires at its end
work with other agents, on any machine messages, and discovery of agents by ID pattern
share scarce resources locks and semaphores
keep going when something breaks retries of failed turns, and resumes of turns cut when OpenCode restarted
ask for a decision without stopping the Inbox: questions, permissions and approvals, which you, another agent or a job's run answer
stay within limits while nobody watches a daily cost cap, compaction and expiry
hand a task to a fresh agent jobs: a fresh agent for each run, on a schedule or when started
stay under your control pause, Stop All, this web UI and the history

Features that do not serve long-running autonomy are left out or kept small, so that what is there stays simple for agents and for you.

Autocode coordinates OpenCode 2 sessions. It has two parts: a server, which keeps the state and serves this web UI, and a plugin, which OpenCode loads on every machine that should use Autocode. The plugin connects each OpenCode server folder to the Autocode server. A session that registers with an ID becomes an agent.

You control it all here: you see every agent, wake and message, pause or stop agents, answer messages in the Inbox and change the settings. Autocode types into a session only while it is idle, and every prompt it types says that it comes from Autocode.

{{ sec.start.n }} {{ sec.start.label }}

Install the server once, connect the OpenCode of each machine, then sign in here.

{{ sec.install.n }} {{ sec.install.label }}

On the Linux machine that should run the server, as the user that should own it: 

./autocode install [--listen ADDRESSES] [--id ID]
  • It copies the binary to ~/.autocode/bin/autocode, sets up a systemd user service, starts it and waits until it answers.
  • --listen sets the addresses: names that share one port, like localhost,tailscale:4848 (the default: this machine and its Tailscale address), or addresses each with a port, like 127.0.0.1:4848,0.0.0.0:4849.
  • --id sets the server's ID. Without it, the ID comes from ~/.autocode/config.json, else from the host name.
  • The service starts at boot only with lingering on: loginctl enable-linger $USER (once, as root). Otherwise it starts when you log in; install tells you which.
  • Check it with autocode info and systemctl --user status autocode. Its log: journalctl --user -u autocode.

{{ sec.connect.n }} {{ sec.connect.label }}

On each machine whose OpenCode (2.2.0 or later) should use Autocode:

autocode plugin install --url http://SERVER:4848 \
  --consumer-token-file FILE --server-id ID
  • The consumer token is in ~/.autocode/consumer.token on the server: copy it into a file on this machine.
  • --server-id makes the plugin and the CLI check that they talk to the right server. --admin-token-file also lets you run your own CLI commands from this machine.
  • It puts the plugin into OpenCode's plugin folder and writes the client config, ~/.autocode/client.json.
  • OpenCode loads the plugin with each folder, when the folder is first used. Restart OpenCode servers that were already running (opencode service restart for the background service; it closes open TUIs), or let their folders reload: OpenCode unloads a folder after an hour unused.
  • Check: the Hosts tab (or autocode hosts) lists the machine's folders as online.

{{ sec['sign-in'].n }} {{ sec['sign-in'].label }}

Open http://SERVER:4848/ and sign in with the admin token, from ~/.autocode/admin.token on the server. The token is kept for this browser tab; tick Stay signed in to keep it on this browser until you sign out. The consumer token and agents' session tokens are refused here.

{{ sec.tokens.n }} {{ sec.tokens.label }}

The server makes the admin and consumer tokens at its first start and keeps only their hashes.

Token Kept In Used By
admin ~/.autocode/admin.token on the server you: the CLI and this web UI, with full control
consumer ~/.autocode/consumer.token on the server the plugin's connection, and your CLI for reading; keep it secret: it can act for any session
session made by the plugin for each session; in its shells that session's tools and scripts

If a session token leaks, replace it: New Token on the Agents tab, or autocode token rotate AGENT. The old one stops working at once.

{{ sec.opencode.n }} {{ sec.opencode.label }}

You work with your agents in OpenCode as usual. Autocode adds tools to every session: ask an agent in plain words, and it uses them.

{{ sec.learn.n }} {{ sec.learn.label }}

  • The plugin adds a skill, autocode: a full guide to wakes, messages and the rest, with examples. An agent loads it with OpenCode's skill tool.
  • Once a session is registered, every model call carries one line that names its agent ID and says to use the autocode_* tools.
  • The tools: autocode_me (register, status, discover other agents, help; list jobs with action=jobs, start one with action=run), autocode_wake (set, list, show, cancel and fire wakes), autocode_message (send, list, read and wait for messages; answer what another agent asks), autocode_lock (acquire, renew, release and list locks) and autocode_approval (ask for an approval and wait for it). autocode_me action=help gives the guide to agents that do not load skills.
  • Agents use the tools in the conversation. The CLI is for their scripts, checks and background jobs, which cannot call tools.

{{ sec.register.n }} {{ sec.register.label }}

An agent registers before it uses wakes and messages. Ask it, for example:

  • Register with Autocode as kaggle:casmi26:lead, as the lead of the CASMI 2026 work.
  • Load the autocode skill, then register as myproject:reviewer.
  • Check your Autocode status and find the other kaggle agents.

An ID has letters, digits, -, _, . and :, with levels split by : (project, role, name). owner and autocode are reserved. An ID stays with its session until the agent or you unregister it, or the session is deleted.

{{ sec.wakes.n }} {{ sec.wakes.label }}

A wake is a prompt that Autocode types into an agent's session later. The agent sets it with a name, a trigger and a text; the same name again replaces it. Ask in plain words, for example:

  • Every 30 minutes, check the training run in runs/ and act on the result.
  • Tomorrow at 08:00, plan the day's submissions.
  • When you have been idle for 2 hours, go on with the task list in TODO.md.
  • Every 15 minutes, but only when there are new files in incoming/, load them.
Trigger Falls Due
every 30m
every 2h from 09:00		 every so long, from when it is set or from a time of day
in 45m once, that long after it is set
at 09:00
at 2026-11-30 18:00		 once: at the next 09:00, or at that date and time
cron "0 9 * * 1-5"
cron "0 9 * * 1-5" Europe/Berlin 		on wall-clock times (minute, hour, day, month, weekday), in the server's time zone unless one is named
idle 30m
idle 30m repeat		 once the session has been idle that long, counted from the end of its last turn (an injected one too) but never from before the wake was set; with repeat, again each time that long has passed, counted from the last time it fell due
fire-only only when fired: by you, another agent or a script

Durations: 90s, 30m, 2h, 1d. Times are in the server's time zone (the timezone setting). An in or at wake is gone once it has run.

A wake can have a check: a shell command that runs first, in the agent's folder and with its Autocode values. A check costs no model calls, so a frequent wake with a check is cheap.

  • exit 0 wakes the agent, with the start of the output in the prompt;
  • exit 1 skips this time;
  • anything else is a failure, and three in a row put an alert in your Inbox;
  • a check is stopped after 60 s (check_timeout).

How wakes are delivered:

  • Only while the session is idle: a wake waits while the agent works or is paused.
  • At most one prompt per min_interval (1 minute by default). What falls due together comes in one prompt.
  • Waiting wakes are merged only when they have the same name: the newest one comes.
  • Fire delivers a wake as soon as the session is idle (and min_interval has passed) and skips its check; the prompt says who fired it.
  • While an agent is in the error state (its last turn failed), its wakes and messages wait and go with the next retry.

{{ sec.messages.n }} {{ sec.messages.label }}

  • Agents send messages to one agent, a pattern (kaggle:*) or a list; a group never includes the sender. A message is a text, up to 32,000 characters.
  • A message to owner comes to your Inbox. Your answer goes back to the agent as a message from the owner. You can also send messages yourself: on the Messages tab, or with autocode send.
  • A new message is announced in the agent's next prompt. A text of up to inline_limit characters (1024 by default) is shown whole; longer ones are listed, and the agent reads them with its tool.
  • An agent can wait for a message inside its tool, up to max_tool_wait (5 minutes by default), at no cost.

{{ sec.locks.n }} {{ sec.locks.label }}

A lock is shared by every agent on the server, on any machine: a mutex (one holder at a time) or a semaphore of N places. Agents take one when only one of them (or N) may do something at a time: use a GPU, submit, refresh shared data. Ask in plain words, for example:

  • Take the lock gpu-0 for 2 hours before you train, and release it when the run ends.
  • Run the evaluations under the semaphore gpu-pool, with 2 places.
  • autocode_lock action=acquire name=gpu-0 ttl=2h: a ttl is required, how long the agent holds it from the grant. The first acquire creates the lock with its capacity, max (1 by default).
  • mode=queue (the default) holds it at once when a place is free and nobody waits, else puts the agent in the queue, in arrival order, and the call returns at once; mode=try holds it now or is refused.
  • renew before the ttl runs out; release when done (or to leave the queue); list shows each lock with its holders and queue. Unregistering releases all of an agent's locks.
  • Autocode tells the agent in a prompt: [autocode] lock "gpu-0" granted when its turn comes, [autocode] lock "gpu-0" expired when its hold ran out and was freed; and, from the Locks tab, [autocode] lock "gpu-0" released by the owner when you release its hold and [autocode] lock "gpu-0": out of the queue when you take it out of the queue.

{{ sec.asks.n }} {{ sec.asks.label }}

A turn can wait for a person: OpenCode's question tool asks something, a tool call needs a permission, or the agent asks for an approval before a step it should not take alone. Autocode brings each to your Inbox, and your answer goes back into the session, where the turn goes on. Until then the agent is waiting: its wakes and messages wait too.

  • Questions: the agent uses the question tool as usual; you see the question with its options. question_mode decides where it goes: ask (you), auto (answered at once with auto_answer_text) or another agent.
  • Permissions: a tool call that needs one (a shell command, an edit outside the project) waits for Allow Once, Allow Always or Reject. permission_mode: ask, approve (allowed once at once) or another agent.
  • Approvals: before a payment, a deployment or deleting data, the agent asks with autocode_approval action=ask text=... options=... expires=1h and waits with action=wait id=...; the answer also comes as a notice, like [autocode] approval "deploy the new model" approved. One that expires counts as rejected. approval_mode: ask, approve or another agent.
  • Another agent can answer for you: a mode of agent:team:lead sends the ask to that agent as a notice. It answers with autocode_message action=answer id=ask_... text=..., or hands it back with action=escalate id=ask_... text=<why>, which adds a note to your Inbox item. You see the ask too, and the first answer counts; only you allow always. A mode of job:<name> sends it to a fresh run of that job instead (see Jobs).

{{ sec.jobs.n }} {{ sec.jobs.label }}

A job is a task for a fresh agent: you set it on a machine's OpenCode folder with a model, a prompt and a trigger (every, at, cron or fire-only). Each run is a fresh session there, registered under the run's ID (the job's name and its start minute in UTC, like daily-report:2026-11-08T17:00 for a 09:00 PST start), with a time limit and a cost cap; its result goes to you, an agent or a group. A job has one run at a time: a scheduled one while another works is skipped, and one asked for is refused.

  • Agents: autocode_me action=jobs lists the jobs, and autocode_me action=run job=daily-report text=... starts one with text added to its prompt; the result comes back as a notice, [autocode] result of run daily-report:....
  • A run ends with autocode_me action=finish result=..., or when it ends a turn with nothing waiting (its last reply is the result). Past its time limit or its cap it fails: you get an alert, and its session is kept until you delete it.
  • question_mode=job:daily-report (or the permission and approval ones) sends each ask to a fresh run of that job.

{{ sec.sees.n }} {{ sec.sees.label }}

Every prompt that Autocode types starts with a line that names its source and why, for example: 

[autocode] wake "check-training"
[autocode] wake "training-done" fired by the owner
[autocode] wake "standup", 2 messages
[autocode] retry 3
[autocode] lock "gpu-0" granted

Below it come the parts: each wake with its text, and each message with its sender and subject; a retry first says what failed and asks the agent to continue where it left off; a lock's notice says until when the agent holds it. What others wrote, and a check's output, is quoted: each such line starts with > , so it cannot pass for Autocode's own words. A last line says that the prompt comes from Autocode, not from you, and how the agent lists its wakes and gets help.

{{ sec.cli.n }} {{ sec.cli.label }}

The same binary is the CLI. It takes the server and the token from its flags (--url, --token), then from AUTOCODE_URL and AUTOCODE_TOKEN, then from the client config, then, on the server machine itself, from ~/.autocode/admin.token. Every command takes --json. Exit codes: 0 done, 1 refused or failed, 2 wrong usage, 3 the server cannot be reached.

{{ sec.scripts.n }} {{ sec.scripts.label }}

In the shells of a registered session the plugin sets AUTOCODE_URL, AUTOCODE_TOKEN, AUTOCODE_SERVER_ID and AUTOCODE_SESSION, and the CLI acts as that agent, never with your tokens. Agents use it in scripts, checks and background jobs, which cannot call tools. In an agent's shell it has three commands; the agent's tools do the rest:

  • autocode me: the agent's status;
  • autocode fire me NAME [--text TEXT]: wake itself now, for example when a job ends;
  • autocode send TO TEXT... [--subject S] [--reply-to ID]: send a message.

For example, a training run that wakes its agent when it ends:

nohup sh -c 'python train.py > log.txt 2>&1
  autocode fire me training-done --text "exit $?"' &

{{ sec.web.n }} {{ sec.web.label }}

The pages with lists load them again every 10 s; the footer says how long ago. An action's result shows in the toolbar, beside its buttons. An agent or host ID links to its page, which highlights its row and scrolls it into view; the browser's back button returns.

{{ sec['web-hosts'].n }} {{ sec['web-hosts'].label }}

One row per OpenCode server folder that the plugin connects from, by machine: status, the OpenCode process (the background service or opencode serve, with its process ID), versions and last seen. "no shell values" under the process means that the shells of that server get no Autocode values (see Troubleshooting). A host's link from the Agents page leads here with its row highlighted.

{{ sec['web-agents'].n }} {{ sec['web-agents'].label }}

The agents by machine, with status (idle, working, waiting, paused, offline or error), host (a link to its row on the Hosts page), folder, session and times. A waiting agent has an ask open in the Inbox; a paused one's tooltip says who paused it: you, Stop All or its daily cost cap. An agent in error (its last turn failed) shows the error type under its status, and when the next retry comes, that one is under way, that the failure is not retried, or that the retries ran out; Retry asks for one now. An agent's link from another page leads here with its row highlighted; a filter that would hide it goes. The filter takes an ID pattern and applies a second after you stop typing. Edit a description, Pause or Resume an agent's injections, give it a New Token, or Unregister it. Stop All pauses every agent and interrupts every running turn, after you confirm; Resume All resumes what Stop All paused.

{{ sec['web-inbox'].n }} {{ sec['web-inbox'].label }}

Messages to you, alerts (a wake whose check failed three times in a row), and asks: questions, permission prompts and approvals that an agent's turn waits for. Sent To says whom an ask went to: you, or another agent (a setting chose it), which may add a note under the title when it cannot answer; you can answer it too, and the first answer counts. A question: click an option, or write your own words and Answer (several questions or choices: fill each, then Answer). A permission: Allow Once, Allow Always (OpenCode saves the rule for the project; only you can allow always) or Reject, with an optional reason. An approval: pick an option if it has some, add a note, then Approve or Reject; one that may expire says when. Answer a message, and the answer goes to the agent as a message from the owner; Close a message or an alert you will not answer. Show Closed lists the answered and closed ones too.

{{ sec['web-messages'].n }} {{ sec['web-messages'].label }}

Every message, newest first, with its state (queued, delivered, read). The Text column shows the first 200 characters of a longer text; click anywhere in its cell to see it whole, and again to fold it. Reading a message here leaves its state. Send a Message opens from its title and sends as the owner, to an ID, a pattern or a list.

{{ sec['web-locks'].n }} {{ sec['web-locks'].label }}

Every lock the agents share: its type (Mutex, or so many places), its holders with when each hold runs out, and its queue in order. The filter takes a pattern of lock names (like gpu-*) and applies a second after you stop typing. Release frees a hold after you confirm: the agent is told and the next in the queue gets it. Remove takes an agent out of the queue after you confirm: the agent is told and the others move up. A lock is gone when nobody holds it or waits.

{{ sec['web-wakes'].n }} {{ sec['web-wakes'].label }}

Every agent's wakes: trigger, next run (an idle wake's if the session stays idle), text and check (a longer one shows its first 200 characters; click anywhere in its cell to see it whole, and again to fold it; the check in a fixed-width font), who set it, when it was last set (Last Set: setting a wake again replaces it, and its schedule starts over) and when it last fired. Fire one now, or Cancel it. Set a Wake sets one for any agent.

{{ sec['web-jobs'].n }} {{ sec['web-jobs'].label }}

The jobs: where each runs (machine and folder), its model, trigger, next run, where its result goes, and its Last Run (a link to that run's row). Run Now starts a run, with the text beside it added to its prompt; Edit fills Set a Job with the job, and Delete removes it after you confirm (its runs' history stays). Set a Job sets one on an online host. Below, the runs, newest first, of every job or the Job you pick: who started each, its state, times, cost, result (a click anywhere in a long one's cell shows it whole) and why one failed or was skipped. A failed run's session is kept; Delete Session removes it.

{{ sec['web-history'].n }} {{ sec['web-history'].label }}

Every event the server noted, newest first, 100 at a time: its time, kind, agent and host (links to their pages), session and data. Agent filters by an ID pattern (like kaggle:*), a second after you stop typing; Kind picks a group (like wake.*) or one kind, with how many there are. The filters stay in the address, so Back and links keep them. A click on a Data cell shows the whole data, the next folds it. Older loads the next 100 under them.

{{ sec['web-settings'].n }} {{ sec['web-settings'].label }}

The server-wide values (change one and Save, or Reset it to its default), the pattern rules, the agents' own values, and Resolved for an Agent: one agent's values and where each comes from. A mode setting (question_mode, permission_mode, approval_mode) is a list of its own values; Agent… or Job… adds a list of the registered agents or the jobs, and one that is gone still shows, marked.

{{ sec.settings.n }} {{ sec.settings.label }}

Every setting has a built-in default. A server-wide value replaces it, a pattern rule (the first that matches) replaces that for its agents, and an agent's own value wins over all. Set them on the Settings tab or with autocode settings set. These are in use now:

Setting Default Description
min_interval 1m at most one prompt per session this often
inline_limit 1024 messages up to this many characters go into the prompt whole
check_timeout 60s a wake's check is stopped after this long
check_output 2000 characters of a check's output put into the prompt
max_tool_wait 5m the longest a tool waits inside a turn, for a message say
timezone the server machine's the zone of at and cron wakes (a cron wake keeps the zone it was set with); server-wide only
history_days 30 days of history kept, with message texts and closed Inbox items; server-wide only
retry_interval 1m how long after a failed turn a retry comes (and between retries)
retry_attempts 0 how many retries come before Autocode stops and tells you (0: no limit)
question_mode ask where questions go: you (ask), answered at once (auto) or agent:<id>
auto_answer_text Act according to your best judgement and safe practices to achieve my goals. the answer of auto
permission_mode ask where permission prompts go: you (ask), allowed once at once (approve) or agent:<id>
approval_mode ask where approvals go: you (ask), approved at once (approve) or agent:<id>
compact_at 50% max 500000 compact a session between turns past this context size: tokens, a share of the model's window, or off
daily_usd off an agent's cost cap per day, in dollars; past it the agent is paused until the next day, a higher cap or Resume
cap_warn 90% warn the agent at this share of its cap
expire_after 14d unregister an agent this long after its session's last turn

listen takes effect at the next start.

{{ sec.trouble.n }} {{ sec.trouble.label }}

Symptom What to Check
An agent seems to ignore Autocode Ask it to load the autocode skill, or to call autocode_me action=help.
A wake does not come Is the agent paused or offline (Agents)? Is its session busy? A wake waits until it is idle. Does its check skip (exit 1) or fail? Was the last prompt less than min_interval ago? The Wakes tab shows its next run and when it last fired.
A machine has no hosts The plugin loads with a folder only once the folder is used: open it in a TUI or send a prompt. Read the plugin's log, ~/.autocode/logs/plugin.log.
The plugin's log says "no client config" Run autocode plugin install on that machine.
The plugin's log says "the server at … is X, not Y" The client config's server_id does not match the server: fix the config or the server's ID.
A host is offline The network or Tailscale between that machine and the server. The plugin retries, waiting longer each time (up to 30 s).
The plugin's log says "superseded by a newer instance" Two OpenCode processes use the same folder. The newest holds the connection; the older one takes over when it is gone. Tools and shell values work in both.
An agent shows offline Its host is offline, or its session was deleted.
An agent shows error Its last turn failed (the error type is under its status, like provider.internal when the model's provider was down). Autocode retries every retry_interval (1m), each retry carrying the wakes and messages that waited, until a turn succeeds or retry_attempts retries ran out. Retry on the Agents page (or autocode retry AGENT) retries now. Failures that come back the same way are not retried, and the Inbox says so: an auth error (provider.auth), an invalid request (provider.invalid-request), the content filter (provider.content-filter), an unknown model (provider.unknown) or an operation it does not support (provider.unsupported-operation); fix the cause, then Retry.
Registering says id_taken The ID belongs to another session that still exists: unregister it there, delete that session, or move the ID with autocode agents register ID --session SES --force.
A tool says session_gone The session was deleted in OpenCode; it never gets a token again.
A shell has no AUTOCODE_TOKEN The plugin sets a session's shell values through the local API of its OpenCode server. Hosts marks a host "no shell values" when it cannot reach that API: a standalone server, or opencode serve without --port or without OPENCODE_SERVER_PASSWORD. Use the background service, or start opencode serve with both. Otherwise the server was not reachable at the session's first shell: open a new shell.
The CLI says "the server at … is X, not Y" The URL answers with another server ID than expected; no token was sent.
autocode install waits and fails journalctl --user -u autocode: a port already in use, or a bad --listen.
