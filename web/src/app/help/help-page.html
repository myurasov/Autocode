{{ sec.what.n }} {{ sec.what.label }}

Autocode is a long-term autonomy support framework for OpenCode 2 agents. It gives them what they need to work on their own for days or weeks, alone or as a team, and keeps them under your control.

It has two parts: a server, which keeps the state and serves this web UI, and a plugin, which OpenCode loads on every machine. A project folder that OpenCode has open is a host; a session that registers with an ID becomes an agent.

What it provides, each for work that goes on with nobody watching:

Feature What It Does
Wakes bring an agent back to its work on a schedule, at a time or when it is idle; a check can skip one
Long commands an agent starts a command that runs for hours and is woken when it ends (a fire-only wake)
Messages agents work as a team: they talk to other agents and to you, and find each other by discovery
Locks and semaphores agents share scarce resources, such as a GPU
Recovery retries of failed turns and resumes of turns that a restart cut
The Inbox an agent asks for a decision and the rest goes on; you, another agent or a job answer its questions, permissions and approvals
Limits a daily cost cap, compaction of long sessions and expiry of old agents
Jobs a task handed to a fresh agent, on a schedule or on request
Control pause, Stop All, this web UI and the history of everything

You control it all here, and still work with your agents in OpenCode as before. Every prompt that Autocode types says that it comes from Autocode.

Not set up yet? Start with {{ sec.start.label }}.

{{ sec.words.n }} {{ sec.words.label }}

  • owner: you, the person who runs Autocode. You sign in with the admin token.
  • session: one OpenCode conversation.
  • turn: one round of work in a session, from a prompt until the model stops and waits.
  • step: one model call inside a turn.
  • agent: a session that has registered with Autocode under an ID such as kaggle:lead.
  • Subagent: a helper session that an agent starts with OpenCode's own subagent tool. It works for its agent.
  • host: one project folder that OpenCode has open, on one machine. A machine usually has several hosts. A host is not a machine.
  • TUI: OpenCode's own screen in a terminal, where you talk to a session.
  • wake: a prompt that Autocode types into an agent's session later, on a schedule or when it has been idle.
  • check: a shell command attached to a wake. Its exit code decides whether the wake is worth a prompt.
  • fire: make a wake due now, without its check.
  • message: text that an agent or you send to another agent or to you.
  • notice: a message that Autocode itself sends to an agent, for example that a lock was granted or an approval was answered.
  • alert: an Inbox item that Autocode raises for you when something needs attention.
  • ask: a question, a permission prompt or an approval that an agent waits on. While it is open, the agent is waiting.
  • lock: a named mutex or semaphore that agents on every machine share.
  • job: a saved task: a prompt, a model, a host and a trigger. A run is one execution of a job, in a fresh session that is an agent for as long as the run lasts.
  • context and compaction: see {{ sec.compaction.label }}.
  • token: two different things. The admin token, the consumer token and a session token are secrets that open the server; see {{ sec.tokens.label }}. Context tokens, written with K and M, measure the size of a context.

{{ sec.daily.n }} {{ sec.daily.label }}

What you do on a normal day: look at the agents' statuses, answer the Inbox, and keep an eye on spend and context. The commands are those of the CLI, ~/.autocode/bin/autocode; see {{ sec.cli.label }}.

{{ sec.statuses.n }} {{ sec.statuses.label }}

The Agents tab shows each agent's status, with a colored dot. autocode agents prints the same.

Status Means What You Do
idle Its session waits for a prompt. Wakes and messages reach it. Nothing.
working A turn is running. Messages join it at its next step; wakes wait until it ends. Nothing. To stop it, see {{ sec.pause.label }}.
waiting It has an ask open: a question, a permission prompt or an approval. Its wakes and messages wait too. Answer the ask in {{ sec.inbox.label }}.
error Its last turn failed. The error type and what comes next are under the status. Usually nothing: Autocode retries. If the line under the status says "not retried" or "retries ran out", fix the cause and click Retry. See {{ sec.retries.label }}.
paused Autocode types nothing into its session. Hover over the status to see who paused it: you, Stop All or its daily cost cap. Click Resume when it should go on.
offline Its host is offline, or its session was deleted in OpenCode. While the host is offline, its wakes and messages wait. See "A host is offline" in {{ sec.trouble.label }}.

When several apply, the later row of the table wins, except that working and waiting win over error. So a paused agent may still be finishing a turn. While a retry runs, the status reads working, with the error type and "retrying now" still under it.

{{ sec.pause.n }} {{ sec.pause.label }}

  • Pause is in the agent's row on the Agents tab; the command is autocode pause AGENT. Autocode stops typing into this agent's session. Its wakes, messages and retries wait; nothing is lost. A turn that is already running goes on to its end. Subagents it started go on too. When one ends, OpenCode starts a turn in the agent to hand over the result; Autocode does not stop that turn.
  • Resume is in the same row (autocode resume AGENT). It delivers what waited.
  • Stop All is at the top of the Agents tab (autocode stop-all). After you confirm, it pauses every agent and interrupts every running turn. Subagents that work for an agent are interrupted too, and so is a job's run that was working.
  • Resume All is beside it (autocode resume-all). It resumes the agents that Stop All paused and delivers what waited. Agents you paused yourself stay paused.
  • A turn that Stop All interrupted is not started again. The agent goes on at its next wake, message or retry, or when you prompt it in OpenCode. An interrupted run does not go on: it fails when its time limit passes, and only then can its job run again.

Stop All leaves these running:

  • Commands that agents started in the background, such as a training run. Autocode stops turns, not processes: stop those on their machine.
  • OpenCode sessions that are not registered as agents.
  • A turn on a host that is offline at that moment. Its agent is paused all the same.
  • The jobs' schedules. A job still starts a run when its trigger falls due, and Run Now still works. To keep a job from starting runs, delete it or set its trigger to fire-only.

Autocode has no button that interrupts the turn of one agent only. Pause the agent, then interrupt its turn in OpenCode itself.

{{ sec.inbox.n }} {{ sec.inbox.label }}

The Inbox tab collects what agents and Autocode want from you. autocode inbox lists the same items, and autocode answer answers them. Autocode sends you no notification: open the web UI to see what came. While something waits for you, the Inbox tab's top edge is red-pink, whichever tab is open.

Kind What It Is What You Do
message An agent wrote to owner. Write an answer and click Answer: it goes to the agent as a message from the owner. Or click Close.
report An agent tells you what it did or found, and needs no answer. It is a message that the agent marked as a report. Read it and click Close, or leave it: it closes by itself after 7 days (report_close_after). You can answer it like a message.
alert Autocode tells you something: a run's result or failure, a wake whose check failed three times in a row, an agent at its daily cap, a failed turn that is not retried, a host whose OpenCode is too old. Read it, act if needed, then click Close.
question An agent's question tool asks you something. Click an option, or write your own words and click Answer. With several questions or choices, fill each, then click Answer.
permission A tool call needs your permission, such as a shell command or an edit outside the project. Click Allow Once, Allow Always or Reject; a reason for Reject is optional. With Allow Always, OpenCode saves the rule for the project; only you can allow always.
approval An agent asks before a step it should not take alone, such as a payment, a deployment or deleting data. A job that an agent wants to set also comes as an approval. Pick an option if it has some, add a note if you like, then click Approve or Reject. One that may expire says when.

If you do not answer:

  • A question, a permission or an approval keeps its agent waiting, and the agent's wakes and messages wait with it. The approval of a job that an agent set is the exception: the agent goes on meanwhile.
  • An approval with an expiry is rejected when the time passes, and the agent is told to treat it as rejected. One without an expiry waits until you answer.
  • A question or a permission also closes when you answer it in OpenCode itself, or when its turn ends. One that a Subagent asked stays open after its agent's turn ended, until it is answered or the Subagent stops.
  • A message or an alert holds nothing up: the agent goes on. Close it when you have read it.

An ask can go to another agent or to a job instead of you; see {{ sec.asks.label }}. The tab's filters and Close All are under {{ sec['web-inbox'].label }}.

{{ sec.spend.n }} {{ sec.spend.label }}

Where you see what the agents cost:

  • The Agents tab, Spend column: today and in total.
  • The Costs tab: every agent's Today, Daily Cap, Last 7 Days and Total. autocode costs prints the same numbers.
  • Yesterday: on the Costs tab, hover over the second bar from the right in the agent's Last 7 Days.
  • Older days: click Days in the agent's row for its spend per day, or run autocode costs kaggle:lead.

A day is the server's day, in its time zone (the timezone setting).

The daily cap is the setting daily_usd; it is off by default. To cap one agent, for example kaggle:lead at $20 a day:

  1. Open the Settings tab and go to Agents' Own Values.
  2. Under its table, enter kaggle:lead in Agent ID, pick daily_usd in Setting and enter 20 in Value.
  3. Click Add. The value shows in the table, and the agent's Daily Cap on the Costs tab shows the cap.

Or with the CLI:

autocode settings set daily_usd 20 --agent kaggle:lead

A cap for a group of agents or for every agent is set like any other setting; see {{ sec.settings.label }}. Such a cap is each agent's own cap. There is no cap on their sum.

What the cap does:

  • At cap_warn (90% of the cap) the agent gets one notice a day, so that it finishes what matters.
  • Past the cap, the agent is paused when its turn ends, and you get an alert.
  • The pause ends in one of three ways: the next day starts, you raise the cap, or you click Resume. After Resume the cap does not pause the agent again that day.
  • A run's cost counts toward the cap of the agent it counts for; see {{ sec.jobs.label }}.
  • What a session spent before it registered counts too. When a session registers for the first time, Autocode reads its earlier steps from OpenCode, those of its Subagents included, and files each one on the day it ran. What it spent earlier today counts toward today's cap. History shows cost.before. For an agent that registered before v1.1.0-rc3, run autocode costs account AGENT.

{{ sec.compaction.n }} {{ sec.compaction.label }}

A session's context is everything the model reads again at each step, counted in tokens. It grows with the conversation, and a model can hold only so much: its window.

The Context column on the Agents tab shows three numbers, like 312K/500K/1M:

  1. what the session holds now;
  2. the size at which Autocode compacts it (compact_at);
  3. the most the model can hold, its window.
  • Hover over the numbers for the exact ones.
  • The bar under them shows how close the session is to compaction: amber from 75%, red from 100%.
  • When the first number passes the second, compaction is due: it comes when the turn ends. It waits while the agent is paused or offline.

Compaction: OpenCode replaces the older part of the session with a summary, so that the session can go on. Details that are not in the summary are no longer in front of the model. That is why Autocode tells the agent first:

  1. Once the context passes compact_at, the agent gets [autocode] compaction next. It comes as soon as the limit is passed, even in the middle of a turn. If the session is idle, for example after a turn you ran yourself in OpenCode, it comes as a prompt of its own.
  2. The agent brings its work to a stable state and writes down what it must remember.
  3. When that turn ends, the session is compacted.
  4. [autocode] compaction done follows. The agent reads its notes and goes on with the steps that are left, or ends its turn when nothing is left.
  • If OpenCode cannot do the compaction, nothing is compacted and no compaction done comes. It is tried again after the next turn that passes the limit.
  • An agent can ask for a compaction itself, with autocode_me action=compact. If OpenCode cannot do that one, the agent gets [autocode] compaction failed and can ask again.

The default compact_at is 50% max 500000: half of the model's window, but at most 500,000 tokens. The table under {{ sec.settings.label }} says what else it takes. For example, for one agent: 

autocode settings set compact_at 90% --agent kaggle:lead

{{ sec.retries.n }} {{ sec.retries.label }}

A turn can fail: the model's provider is down, a request is refused, a reply is blocked. The agent then shows error, with the error type under its status, like provider.internal.

  • Autocode retries by itself. It types a retry prompt every minute (retry_interval). The prompt starts with [autocode] retry and the retry's number, like [autocode] retry 3. It says what failed and asks the agent to continue where it left off. The messages and the wakes that waited come with it; a wake with a check waits until the agent works again.
  • retry_attempts sets how many retries come before Autocode stops and tells you. The default, 0, is no limit.
  • Under the status one of four things shows: when the next retry comes ("retry 3 in 40s"), that one is running ("retrying now", under the status working), that this failure is not retried ("not retried"), or that the retries ran out ("retries ran out"). A blocked reply has "blocked:" before it, and can also say that a compaction comes.
  • Retry, in the agent's row for as long as the error shows, tries again now. So does autocode retry AGENT.

Some failures come back the same way, so Autocode does not retry them and puts an alert in your Inbox:

  • provider.auth: the provider refused the sign-in;
  • provider.invalid-request: an invalid request;
  • provider.unknown: an unknown model;
  • provider.unsupported-operation: something the model does not support.

Fix the cause, then click Retry. The alert closes by itself once the agent works again.

  • A reply that the provider's content filter blocked (provider.content-filter) is retried once, asking the agent for other, shorter words. If it is blocked again, the session is compacted and retried once more. After that you get an alert. filter_recovery sets how far this goes: retry compact (both steps, the default), retry (the first step only) or off.
  • A turn that was cut because OpenCode restarted is resumed: once OpenCode is back, [autocode] resume tells the agent to continue where it left off.
  • After a power cut or a reboot of the server's machine, Autocode starts OpenCode's background service again by itself for every folder with something unfinished: a wake or message that waits, a turn that was running, a prompt or a check that was on its way. Nobody has to open OpenCode. A turn that was running goes on: OpenCode resumes it itself, or Autocode's resume prompt does.

{{ sec.opencode.n }} {{ sec.opencode.label }}

Autocode adds tools to every session: ask an agent in plain words, and it uses them. Each part starts with what you can say; what the agent calls comes after.

{{ sec.register.n }} {{ sec.register.label }}

An agent registers before it uses wakes and messages. Ask it, for example:

  • Register with Autocode as kaggle:housing:lead, as the lead of the housing prices work.
  • Load the autocode skill, then register as myproject:reviewer.
  • Check your Autocode status and find the other kaggle agents.
  • An ID has letters, digits, -, _, . and :. The colons split it into levels, such as project, role and name.
  • owner, autocode and IDs that start with job: are reserved.
  • An ID stays with its session until the agent or you unregister it. If the session is deleted in OpenCode, the agent stays listed, as offline. No other session can register under an ID that is registered: only you move it to another session, with autocode agents register ID --session SES (and --force while the old session still exists).
  • When it registers, the session's title becomes @ and its ID, like @kaggle:housing:lead, so you find it in OpenCode's list of sessions.
  • An agent is unregistered 14 days after its session's last turn (expire_after), unless you or Stop All paused it.
  • To change an agent's ID, rename it: ask the agent ("Rename yourself to kaggle:lead"), or run autocode agents rename AGENT NEW-ID. The agent stays what it is, and its wakes, waiting messages, locks, spend, settings and jobs come along. A message sent to the old ID still reaches the agent. Unregistering and registering again would remove its wakes and start its spend over.

{{ sec.wakes.n }} {{ sec.wakes.label }}

A wake is a prompt that Autocode types into an agent's session later. A wake has a name, a trigger and a text; setting the same name again replaces it. Ask the agent in plain words, for example:

  • Every 30 minutes, check the training run in runs/ and act on the result.
  • Tomorrow at 08:00, plan the day's submissions.
  • When you have been idle for 2 hours, go on with the task list in TODO.md.
  • Every 15 minutes, but only when there are new files in incoming/, load them.

You can also set a wake for any agent yourself: Set a Wake on the {{ sec['web-wakes'].label }}, or autocode wake set.

Trigger Falls Due
every 30m
every 2h from 09:00		 again and again, that long apart, counted from when it is set or from a time of day
in 45m once, that long after it is set
at 09:00
at 2026-11-30 18:00		 once: at the next 09:00, or at that date and time; a time that has passed is refused
cron "0 9 * * 1-5"
cron "0 9 * * 1-5" Europe/Berlin 		on wall-clock times (minute, hour, day, month, weekday), in the server's time zone unless one is named
idle 30m
idle 30m repeat		 once in each idle stretch: when the session has done nothing for that long. The time counts from the end of its last turn, also of a turn this wake started, or from when the wake was set if that is later. With repeat, again within one stretch, each time that long passes.
fire-only only when fired: by you, another agent or a script
fire-only once the same, for one fire: the wake is removed when it is fired, and its prompt still comes. For a command that ends once.

Durations: 90s, 30m, 2h, 1d. Times are in the server's time zone (the timezone setting). An in or at wake is gone once it has fallen due.

A wake can have a check: a shell command that runs first, in the agent's folder, with what an agent's shell has (see {{ sec.scripts.label }}). The check runs in bash. A check costs no model calls, so a frequent wake with a check is cheap. Its exit code decides:

  • exit 0 wakes the agent, with the start of the output in the prompt;
  • exit 1 skips this time;
  • anything else is a failure, and three in a row put an alert in your Inbox;
  • a check is stopped after 60 s (check_timeout), which counts as a failure.

A check may do the routine pass itself. A wake that mostly finds nothing to do costs a whole turn each time; with its script as the check, a pass that finds nothing costs no model call. The script exits 0, with what the agent must know in its output, only when something needs the agent. Such a check may need minutes: a wake can carry its own time limit, at most 10 minutes (check_timeout_max). Ask the agent for it, fill in Check Timeout in the form, or use --check-timeout 5m.

For example, wake an agent every 30 minutes, but only when results.csv has changed since the last time: 

autocode wake set kaggle:lead results --trigger "every 30m" \
  --text "results.csv changed: read it and plan the next run." \
  --check "test results.csv -nt .seen && touch .seen"
  • test results.csv -nt .seen exits 0 only when results.csv is newer than the marker .seen, or when the marker does not exist yet. Then touch renews the marker, the check exits 0 and the agent wakes.
  • Otherwise the check exits 1: nothing is typed and no model call is made.

How wakes are delivered:

  • Only while the session is idle: a wake waits while the agent works, waits for an answer, is paused or is offline.
  • At most one prompt per min_interval (1 minute by default). What falls due together comes in one prompt.
  • Waiting wakes are merged only when they have the same name: the newest one comes.
  • Fire delivers a wake as soon as the session is idle and min_interval has passed. It skips the check, and the prompt says who fired it.
  • Every prompt from Autocode ends with two lines: the server's time, the agent's context and what it spent today; then Autocode's name and where the agent gets help. So an agent need not ask for its status to learn them.

{{ sec.messages.n }} {{ sec.messages.label }}

Agents write to each other and to you. Ask in plain words, for example:

  • Tell kaggle:worker that the new features are ready.
  • Send every kaggle agent the new deadline.
  • Ask the owner whether to submit today, and wait for the answer.
  • A message is a text, up to 32,000 characters. It goes to one agent, to a pattern or to a list. The sender never gets its own message.
  • You can write to agents yourself: Send a Message on the {{ sec['web-messages'].label }}, or autocode send: 
autocode send 'kaggle:*' "The deadline moved to Friday."

Whom a message reaches. In a pattern, * stands for any characters, colons too:

To Reaches
kaggle:lead that one agent
kaggle:* every agent whose ID starts with kaggle:, so kaggle:lead and also kaggle:housing:lead
*:lead every agent whose ID ends in :lead
kaggle:lead,kaggle:worker both; a list is split by commas and may hold patterns
owner you, in the Inbox

A message to one ID that is not registered is refused. In a list, such an ID is skipped.

How a message arrives:

  • A new message comes whole. An agent that is working gets it in the same turn, at its next step, together with Autocode's notices. An idle agent gets it as a new prompt.
  • An agent can also take its messages itself: autocode_message action=list shows what waits, action=read takes it now, whole, and action=wait waits for one (at most max_tool_wait), by sender or by the message it answers. A message is processed once: what read or wait took never comes in a prompt.
  • Agents are told to write to you briefly: the point first, only what you need to know or decide, and the options.
  • The Messages tab shows what became of each message.

{{ sec.locks.n }} {{ sec.locks.label }}

A lock is shared by every agent on the server, on any machine: a mutex (one holder at a time) or a semaphore of N places. Agents take one when only one of them, or N, may do something at a time: use a GPU, submit, refresh shared data. Ask in plain words, for example:

  • Take the lock gpu-0 for 2 hours before you train, and release it when the run ends.
  • Run the evaluations under the semaphore gpu-pool, with 2 places.
  • Unregistering releases all of an agent's locks.
  • On the {{ sec['web-locks'].label }} you see every lock, and can free a hold or take an agent out of the queue.

What the agent calls:

  • autocode_lock action=acquire name=gpu-0 ttl=2h: a ttl is required, how long the agent holds the lock from the grant. The first acquire creates the lock with its capacity, max (1 by default).
  • mode=queue (the default): the agent gets the lock at once if a place is free and nobody waits. Otherwise it joins the queue, in arrival order, and is told when its turn comes.
  • mode=try: it gets the lock now or is refused.
  • renew before the ttl runs out; release when done, or to leave the queue; list shows each lock with its holders and queue.

What Autocode tells the agent, in a prompt:

  • [autocode] lock "gpu-0" granted: its turn came;
  • [autocode] lock "gpu-0" expired: its hold ran out and was freed;
  • [autocode] lock "gpu-0" released by the owner: you freed its hold on the Locks tab;
  • [autocode] lock "gpu-0": out of the queue: you took it out of the queue there.

{{ sec.asks.n }} {{ sec.asks.label }}

A turn can wait for a person. Autocode calls each such wait an ask: a question from OpenCode's question tool, a permission that a tool call needs, or an approval that the agent asks for before a step it should not take alone. Tell an agent when to ask for approval, for example:

  • Ask for my approval before you submit to the leaderboard.
  • Before you delete anything in data/, ask for my approval; if I do not answer within an hour, do not delete.

Autocode brings each ask to your Inbox, and your answer goes back into the session, where the turn goes on. Until then the agent is waiting. How to answer, and what happens when you do not, is under {{ sec.inbox.label }}.

Three settings decide who answers: question_mode, permission_mode and approval_mode. Each is ask (you) by default, and can be:

  • auto, for questions only: Autocode answers at once with the text in auto_answer_text;
  • approve, for permissions and approvals: Autocode allows once, or approves, at once;
  • agent:team:lead: the ask goes to that agent. You see it too, and the first answer counts. Only you can answer Allow Always;
  • job:<name>: the ask goes to a fresh run of that job.

What the agents call:

  • For an approval: autocode_approval action=ask text=... options=... expires=1h, then action=wait id=.... The answer also comes as a notice, like [autocode] approval "deploy the new model" approved.
  • expires is optional, from 1 second to 30 days.
  • The agent that an ask was sent to answers with autocode_message action=answer id=ask_... text=.... It hands the ask back with action=escalate id=ask_... text=<why>, which adds a note to your Inbox item.

{{ sec.jobs.n }} {{ sec.jobs.label }}

A job is a saved task for a fresh agent: a prompt, a model, a host (the folder it runs in) and a trigger. Each run is a fresh session in that folder, registered as an agent for as long as the run lasts. Its result goes to you, to an agent or to a group.

For example, a report every morning at 9, sent to you:

autocode job set daily-report --host HOST --model MODEL \
  --prompt "Sum up yesterday's work in this folder in 10 lines." \
  --trigger 'cron "0 9 * * *"'
  • HOST is the ID of the folder the job runs in, like laptop:housing:1a2b3c4d. Take it from the ID column of the Hosts tab or of autocode hosts.
  • MODEL is provider/model as OpenCode names it, like openai/gpt-5. An agent's Model on the Agents tab shows it in this form.
  • The job runs every day at 09:00, in the server's time zone.
  • Without --to the result goes to you: it comes to your Inbox as an alert, "Result of run daily-report:...". --to myproject:reviewer sends it to that agent instead; a pattern or a list works too.
  • To check: autocode job list shows the job and its next run. autocode job run daily-report starts a run now. Set a Job and Run Now on the {{ sec['web-jobs'].label }} do the same.

A job's trigger is one of these:

Trigger Runs
cron "0 9 * * *" every day at 09:00; cron "0 9 * * 1-5" on weekdays only
every 6h again and again, 6 hours apart, counted from when the job is set
at 09:00 once, at the next 09:00; the job stays, with no next run
fire-only only when started: by Run Now, autocode job run, an agent or an ask

idle is for wakes only. The trigger table under {{ sec.wakes.label }} has every other form.

How runs go:

  • A run's ID is the job's name and the minute it started, in UTC. A run started at 09:00 Pacific Standard Time is daily-report:2026-11-08T17:00.
  • A job has one run at a time: a scheduled one while another works is skipped, and one asked for is refused.
  • A run ends when its agent calls autocode_me action=finish result=..., or when its turn ends with nothing left to wait for; then its last reply is the result. A run does not end while a Subagent it started still works, or while OpenCode's image tool is still making an image for it.
  • A run has a time limit (--timeout, 1 hour by default) and can have a cost cap in dollars (--run-usd; Run Cap on the Jobs tab). Past either it fails: you get an alert, and its session is kept until you delete it.
  • The session of a run that succeeded is deleted, unless the job was set with --keep-session.
  • A run whose host is offline waits for it, up to its time limit.

Who pays for a run:

  • A run of an agent's own job counts for that agent, whoever started it; scheduled runs too.
  • A run of a job of yours counts for the agent that started it. One started by another run counts as that run does; one that answers an ask counts for the agent that asked.
  • Runs of your jobs that you or a schedule started count for the job's own row on Costs, job:<name>.
  • What counts for an agent is added to its Today and Total, and counts toward its daily cap.

Agents and jobs:

  • autocode_me action=jobs lists the jobs, and autocode_me action=run job=daily-report text=... starts one with text added to its prompt. The result comes back to that agent as a notice, [autocode] result of run daily-report:....

  • With job_mode ask (the default) an approval in your Inbox shows the whole definition, and the job exists once you approve it. approve sets it at once; off refuses.
  • An agent's jobs go when it unregisters.

{{ sec.settings.n }} {{ sec.settings.label }}

Every setting has a built-in default. For an agent, Autocode uses the first of these that exists:

  1. the agent's own value;
  2. the first rule whose pattern matches its ID, like kaggle:*;
  3. the server-wide value;
  4. the built-in default.

Set them on the {{ sec['web-settings'].label }}, or with the CLI: 

autocode settings set min_interval 5m
autocode settings set daily_usd 20 --match 'kaggle:*'
autocode settings set daily_usd 50 --agent kaggle:lead
autocode settings unset daily_usd --agent kaggle:lead
autocode settings --agent kaggle:lead
  • The first three set a value: server-wide, as a rule for a pattern, and for one agent. Keep the quotes around a pattern: without them the shell may change the *.
  • The fourth takes the agent's value away again. The last shows the agent's values and where each comes from.
  • A change applies at once.

{{ sec.trouble.n }} {{ sec.trouble.label }}

Symptom What to Check
Signing In
I cannot sign in, or I lost the admin token
  1. Sign in with the admin token. It is not lost while its file exists: read it on the server machine, cat ~/.autocode/admin.token. The consumer token and session tokens are refused here.
  2. If that file is gone, find a machine where your own commands still work because its client config, ~/.autocode/client.json, holds the admin token. Run autocode token rotate --admin there. The server makes a new admin token, saves it in ~/.autocode/admin.token on the server machine and prints that path. The old token stops working at once.
  3. If no machine has the admin token any more, no command recovers it: make the server create a new one. On the server machine, stop the autocode service, copy the database as a backup, delete the old token's record and start the service again. It needs the sqlite3 tool. The server makes a new admin.token when it starts. After an install with --data DIR, the database and admin.token are in DIR, not in ~/.autocode. 
    systemctl --user stop autocode
cp -p ~/.autocode/autocode.db ~/.autocode/autocode-backup.db
sqlite3 "$HOME/.autocode/autocode.db" \
  "DELETE FROM tokens WHERE kind = 'admin'"
systemctl --user start autocode
Agents
Something is going wrong and everything should stop Click Stop All at the top of the Agents tab, or run autocode stop-all. What it stops, and what it leaves running, is under {{ sec.pause.label }}.
An agent seems to ignore Autocode Ask it to load the autocode skill, or to call autocode_me action=help.
An agent shows paused, and you did not pause it Hover over its status. "Paused by Stop All": click Resume All. "Paused by its daily cost cap": it goes on the next day; to let it go on now, raise daily_usd or click Resume.
An agent shows offline Its host is offline (see "A host is offline"), or its session was deleted in OpenCode.
An agent shows error Its last turn failed. If the line under its status says that a retry is coming, wait. If it says "not retried" or "retries ran out", fix the cause, then click Retry on the Agents tab or run autocode retry AGENT. What each error type means is under {{ sec.retries.label }}.
Registering says id_taken The ID is registered already, to another session: choose another ID, unregister the agent that holds it, or move the ID to the new session with autocode agents register ID --session SES (with --force when the old session still exists).
A tool says session_gone The session was deleted in OpenCode; it never gets a token again.
A shell has no AUTOCODE_TOKEN The plugin can put Autocode's values into shells only when OpenCode runs as its background service, or as opencode serve started with --port and with a password in OPENCODE_PASSWORD or OPENCODE_SERVER_PASSWORD. Otherwise the Hosts tab marks the host "no shell values": run OpenCode in one of these two ways. A host marked "too old" gets no values either. Wakes
A wake does not come

  2. Is the agent working, or waiting for an answer? A wake waits until the session is idle.
  3. Does its check skip (exit 1) or fail? Run the check by hand in the agent's folder.
  4. Was the last prompt less than min_interval ago?
  5. The Wakes tab shows when it falls due next and when it last fired. The History tab, with the agent and the Kind wake.*, shows what happened to it.
Hosts and Machines
A machine has no hosts The plugin loads with a folder only once the folder is used: open it in a TUI or send a prompt. If no host shows then, read the plugin's log on that machine, ~/.autocode/logs/plugin.log.
A host is offline A host is one folder, not the machine. The Hosts tab lists an offline one only with the Offline box ticked. Check in this order:
  1. Is OpenCode running on that machine? Start it.
  2. Was the folder unused for an hour? OpenCode unloads such a folder. Open it in a TUI or send it a prompt. On the server's own machine, Autocode loads the folder again by itself when the host has something unfinished, if OpenCode runs as the background service.
  3. Is the host marked "too old" on the Hosts tab? See the next row.
  4. Can that machine reach the server? Run autocode info there: it must answer. If not, check the network, or Tailscale if you use it. The plugin retries by itself, waiting longer each time, up to 30 s.
  5. Read the plugin's log on that machine, ~/.autocode/logs/plugin.log.
A host is marked "too old", or a tool says "this OpenCode is v2.2.0; Autocode needs v2.3.0 or later" That machine's OpenCode is older than Autocode can use; the mark names the version it needs. Update OpenCode there and start it again: opencode service restart for the background service. Until then Autocode does nothing for that host. The host and its agents show offline, and the agents' wakes and messages wait until it is back. The autocode_* tools answer with the reason. Its sessions' tokens stop working and its shells get no Autocode values. OpenCode itself still works, so you can go on in those sessions by hand; other machines' hosts are not touched. You get one Inbox alert for the host and its OpenCode version; once closed it does not come again for history_days days. The Hosts tab keeps the mark.
autocode install waits and fails Read the server's log, journalctl --user -u autocode. The usual causes: the port is already in use, or --listen is wrong.
The CLI says "the server at … is X, not Y" The URL answers with another server ID than the one expected, so the CLI sent no token. Check --url and --server-id, or the server_id in ~/.autocode/client.json.
The Plugin's Log, ~/.autocode/logs/plugin.log
The plugin's log says "no client config" Run autocode plugin install on that machine.
The plugin's log says "the server at … is X, not Y" The client config's server_id does not match the server: fix the config or the server's ID.
The plugin's log says "superseded by a newer instance" Nothing is wrong. Two OpenCode processes have the same folder open. The newest one keeps the connection, and the older one takes over when the newest is gone. Tools and shell values work in both.

{{ sec.cli.n }} {{ sec.cli.label }}

  • The CLI is the same binary as the server. It is in ~/.autocode/bin/autocode on every machine where you ran autocode install or autocode plugin install.
  • Nothing changes the PATH of your own terminal. Type the whole path, or add the folder once and open a new terminal: 
echo 'export PATH="$HOME/.autocode/bin:$PATH"' >> ~/.bashrc
  • The server it talks to: --url, else AUTOCODE_URL, else the client config, ~/.autocode/client.json, else this machine.
  • Every command that prints data takes --json.
  • Exit codes: 0 done, 1 refused or failed, 2 wrong usage, 3 the server cannot be reached.

The token it uses is the first of these that exists:

  1. --token;
  2. AUTOCODE_TOKEN, which an agent's shell has;
  3. the admin token in the client config;
  4. the server's own ~/.autocode/admin.token, when the URL is this machine's (127.0.0.1 or localhost);
  5. the consumer token in the client config, which is enough for info, hosts, agents, costs, settings (to read) and history; every other command is refused.

So your commands work on the server machine when its client config's URL is http://127.0.0.1:4848, as in {{ sec.connect.label }}, and on every machine whose plugin was installed with --admin-token-file.

{{ sec.scripts.n }} {{ sec.scripts.label }}

In the shells of every session of a connected folder, and in wake checks, the plugin sets four values: AUTOCODE_URL, AUTOCODE_TOKEN, AUTOCODE_SERVER_ID and AUTOCODE_SESSION. It also puts ~/.autocode/bin first in their PATH, so a script calls autocode by name. There the CLI acts as that agent, never with your tokens.

Agents use it in scripts, checks and long commands, which cannot call tools. In an agent's shell it has three commands for the agent, besides info and the machine's set-up commands; the agent's tools do the rest:

  • autocode me: the agent's status;
  • autocode fire me NAME [--text TEXT]: wake itself now, for example when a long command ends;
  • autocode send TO TEXT... [--subject S] [--reply-to ID] [--report]: send a message. --report marks one to you that needs no answer.

For example, a training run that wakes its agent when it ends:

nohup sh -c 'python train.py > log.txt 2>&1
  autocode fire me training-done --text "exit $?"' &

The agent sets the wake first, with the trigger fire-only once and the name training-done. The wake is removed when the command fires it.

{{ sec.start.n }} {{ sec.start.label }}

You need this once: install the server, connect the OpenCode of each machine, then sign in. The examples call the server machine machine-a, a second machine machine-b and the server home.

{{ sec.install.n }} {{ sec.install.label }}

On machine-a, the Linux machine that should run the server, as the user that should own it: 

dist/autocode install --id home --listen localhost,tailscale:4848
  • dist/autocode is the binary you built from the source. The README at github.com/myurasov/Autocode says how.
  • --id names the server. Without it, the ID comes from ~/.autocode/config.json, else from the host name.
  • --listen sets the addresses. localhost,tailscale:4848 is this machine and its address in Tailscale, a private network between your machines, both on port 4848; it is also the default. On a LAN without Tailscale use --listen 0.0.0.0:4848. Addresses can each have a port: 127.0.0.1:4848,0.0.0.0:4849.
  • --data DIR keeps the server's data, with admin.token and consumer.token, in DIR. Then read the tokens there, and give the CLI the admin token with --admin-token-file DIR/admin.token at plugin install: it looks for the server's own token only in ~/.autocode/.
  • The command copies the binary to ~/.autocode/bin/autocode, sets up a systemd user service, autocode.service, starts it and waits until it answers. Then it prints where the tokens are.
  • The service starts at boot only with lingering on: sudo loginctl enable-linger $USER, once. Otherwise it starts when you log in; install tells you which.
  • To check: ~/.autocode/bin/autocode info prints the server's ID and version, and systemctl --user status autocode says active. The server's log: journalctl --user -u autocode.
  • ~/.autocode/bin/autocode uninstall removes the service; the binary and the data stay.

{{ sec.connect.n }} {{ sec.connect.label }}

Do this on each machine whose OpenCode (2.3.0 or later) should use Autocode, as the user who runs OpenCode there. Add ~/.autocode/bin to your PATH first (see {{ sec.cli.label }}), or type the whole path. On machine-a, where the binary and the consumer token already are: 

autocode plugin install --url http://127.0.0.1:4848 --server-id home \
  --consumer-token-file ~/.autocode/consumer.token

On machine-b, copy the binary and the consumer token from machine-a first: 

mkdir -p ~/.autocode && chmod 700 ~/.autocode
scp -p machine-a:.autocode/bin/autocode ~/autocode
scp -p machine-a:.autocode/consumer.token ~/.autocode/consumer.token
~/autocode plugin install --url http://machine-a:4848 --server-id home \
  --consumer-token-file ~/.autocode/consumer.token

Then, on either machine:

  1. Start OpenCode again if it was running: opencode service restart for the background service; it closes open TUIs.
  2. Open a folder in OpenCode. It worked when the Hosts tab, or autocode hosts, lists the folder as online.
  • The command puts the plugin into OpenCode's plugin folder, writes the client config, ~/.autocode/client.json, and copies the binary to ~/.autocode/bin/autocode. On machine-b you can delete ~/autocode after it.
  • --server-id makes this machine refuse a server that has another ID.
  • On machine-a every command of yours works. To run them all from machine-b too, copy admin.token the same way and add --admin-token-file ~/.autocode/admin.token.
  • OpenCode loads the plugin with each folder, when the folder is first used.

{{ sec['sign-in'].n }} {{ sec['sign-in'].label }}

  • Open http://machine-a:4848/ in a browser and sign in with the admin token. It is in ~/.autocode/admin.token on machine-a.
  • The token is kept for this browser tab. Tick Stay signed in to keep it in this browser until you sign out.
  • If you cannot sign in, see {{ sec.trouble.label }}.

{{ sec.tokens.n }} {{ sec.tokens.label }}

These tokens are secrets. The server makes the admin and the consumer token at its first start and saves each in a file that only you can read. It cannot show a token again.

The admin token is not lost while its file exists: read it with cat ~/.autocode/admin.token on the server machine. If the file is gone, follow "I cannot sign in, or I lost the admin token" in {{ sec.trouble.label }}.

Token Kept In Used By
admin ~/.autocode/admin.token on the server you: the CLI and this web UI, with full control
consumer ~/.autocode/consumer.token on the server the plugin's connection, and a few commands of your CLI that only read (see {{ sec.cli.label }}); keep it secret: it can act for any session
session made by the plugin for each session; in its shells that session's tools and scripts

If a token leaks, replace it. The old one stops working at once.

  • A session token: New Token on the Agents tab, or autocode token rotate AGENT. The plugin gives the session the new one.
  • The consumer token: autocode token rotate --consumer. Every session token stops working with it. The plugins get new ones by themselves when they reconnect, and shells and checks that start afterwards carry the new token.
  • The admin token: autocode token rotate --admin. Then sign in to the web UI again. If it leaked, replace the consumer token too: with the admin token one could make a new consumer token.
  • The last two save the new token in its file on the server and print that path, never the token.

After a new consumer token:

  1. On every other machine, copy the new ~/.autocode/consumer.token from the server and run autocode plugin install again with it. Until a machine has the new token, its hosts are offline.
  2. OpenCode needs no restart: a running plugin picks the new token up within about a minute.
  3. The machine you ran the command on needs nothing: the command updates its client config, if that config has the URL the command used.
  4. A command that an agent started before the rotation keeps the old token: its autocode fire me ... is refused. Ask the agent to look at the commands it left running, or fire that wake yourself with autocode fire AGENT WAKE.

After a new admin token, on other machines whose client config holds the admin token, run autocode plugin install again with --admin-token-file.

Both commands need the admin token themselves.
